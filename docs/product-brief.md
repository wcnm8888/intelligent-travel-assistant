# 产品说明：Intelligent Travel Assistant

## 产品定位

Intelligent Travel Assistant 是一个仅在本地运行、面向中国大陆境内自由行的旅行决策辅助工具。它帮助个人和小型同行群体把分散的需求、天气、地点、路线、时间和费用信息整理为一份可检查、可解释、可局部修改的结构化旅行计划。

本产品不是自动下单平台，也不是只靠大模型生成文字的旅行灵感工具。它的核心价值是把大模型的需求理解和规划能力，与确定性代码校验、真实数据来源、费用可信状态和失败降级结合起来。

## 目标用户

- 独自旅行、情侣、家庭或小型朋友群体；
- 愿意自行完成酒店、车票和门票预订，但需要决策支持的用户；
- 关心预算是否完整、路线是否合理、数据是否过期的用户；
- 希望修改某一天或某个景点，而不想整份行程从头生成的用户。

不面向旅行社批量运营、企业差旅审批、大型团队调度或跨境旅行合规场景。

## 用户问题

自由行规划通常同时受到日期、开放时间、天气、交通耗时、地理位置、预算和个人偏好的约束。普通攻略难以保持时效，纯文本大模型又可能遗漏费用、编造事实、忽略路线冲突，或在局部修改时无意改变整份计划。

用户需要的不是更多景点名称，而是一份能够回答以下问题的决策材料：

- 这一天为什么这样安排？
- 景点、天气和路线信息来自哪里，何时获取？
- 时间和路线上是否存在明显冲突？
- 总预算包含了哪些费用，哪些只是估算，哪些仍未知？
- 外部数据获取失败时，哪些结论仍可信？
- 修改一个景点会影响当天、住宿城市还是相邻日期？

## 核心场景

### 场景 1：从需求生成初始计划

用户输入目的地、日期、总预算、同行人数、兴趣偏好、节奏、交通和住宿要求。系统补齐必要信息，获取外部数据，生成逐日计划，并用代码校验日期、时间、路线和预算。

### 场景 2：比较计划与约束

用户查看每天的活动、交通段、预计耗时、费用、天气影响和来源记录。系统显式显示冲突、未知费用、过期数据和不能保证的部分，而不是隐藏在自然语言中。

### 场景 3：局部重规划

用户替换某一天的景点、调整时间或删除活动。若影响只在当天内部，系统可自动重新排序并校验；若影响住宿城市、跨城交通或相邻日期，系统必须先展示影响范围并请求确认。

### 场景 4：外部服务降级

天气、地图、路线或模型服务失败时，系统保留已经验证的数据，标记缺失项和更新时间，给出可重试或需要用户补充的信息，不返回假成功计划。

## 术语

- **POI（Point of Interest）**：地图中的地点实体，例如景点、餐厅、酒店、车站或商场。POI 数据通常包含名称、类别、地址、坐标和提供方标识，但不等同于实时价格、库存或营业承诺。
- **结构化旅行计划**：可由程序读取和校验的旅行请求、逐日安排、交通段、费用项、来源和冲突集合，不只是自然语言文章。
- **局部重规划**：基于现有计划版本，只重新计算明确受影响的日期和项目，同时保留其他已确认部分。
- **数据来源记录**：说明提供方、获取时间、有效期、原始标识和警告的信息。

## MVP 范围

MVP 计划提供：

1. 收集并规范化目的地、日期、预算、同行人数、偏好、交通和住宿要求；
2. 通过高德获取地理编码、基础 POI、地点详情和路线信息；
3. 通过和风天气获取天气预报和预警；
4. 通过 DeepSeek `deepseek-v4-flash` 理解需求、编排工具、提出计划并生成解释；
5. 生成包含逐日安排、路线段、费用项、来源和警告的结构化计划；
6. 使用确定性代码校验日期、持续时间、空间顺序、预算完整性和约束冲突；
7. 支持当天内部自动局部重规划，以及跨日或跨城变更前的人机确认；
8. 用轻量 Web UI 展示输入、处理中状态、计划、预算、来源、冲突和重规划结果；
9. 在外部 API 超时、限流、鉴权失败、数据缺失或响应不合法时提供明确降级。

## 费用范围与可信状态

预算覆盖以下全部类别：

- 住宿；
- 城际交通；
- 市内交通；
- 景点或活动门票；
- 餐饮；
- 用户明确加入的其他旅行费用。

每个费用项必须使用以下状态之一：

| 状态 | 含义 | 金额要求 |
| --- | --- | --- |
| `verified` | 来自可追溯数据源，并满足项目定义的时效条件 | 有金额和来源 |
| `estimated` | 基于规则或明确假设计算，不能当作报价 | 有金额、假设和估算时间 |
| `user_provided` | 由用户提供或确认 | 有金额并记录用户输入 |
| `unknown` | 当前无法可靠取得或估算 | 金额必须为空，不得写成 `0` |

总预算结果必须同时展示已知合计、未知项数量和预算是否可判定。存在 `unknown` 时，只能说明“已知部分是否超预算”，不能宣称完整总价低于预算。

酒店第一版只提供高德基础 POI、区域建议、用户输入价格或明确标注的估算。不提供实时房价、库存、可订状态或预订能力。

## 成功标准

产品达到 MVP 成功标准时，应能证明：

- 用户输入可以转成明确的结构化请求，缺少必填约束时不会静默猜测；
- 每个计划日与旅行日期一致，活动和交通段具有可检查的时间顺序；
- 预算包含全部费用类别，未知费用不会被当作零；
- 外部事实带有来源、获取时间、有效期或无法确定有效期的说明；
- 计划冲突由代码产生结构化结果，大模型不能覆盖校验失败；
- 当天内部修改不会无理由重写其他日期；跨日、跨城或住宿变更会先请求确认；
- 至少一种外部服务失败时，用户仍能看到部分结果、影响范围和恢复动作；
- 用户能区分事实、估算、本人输入和未知信息。

具体测试分层、数据集和门禁由 `docs/testing-strategy.md` 在 B-000 Step 6 定义。

## 非目标

MVP 明确不做：

- 自动预订、支付、出票、退改或订单管理；
- 登录、复杂账户体系、多人实时协作和云同步；
- 酒店、机票、火车票或门票实时库存承诺；
- 复杂地图交互、图片内容、PDF 导出和公开分享页；
- 公网部署和面向生产流量的高可用架构；
- 境外目的地、签证、汇率、跨境数据或海外地图合规；
- 多 Agent 协作；
- 把第三方 API 全部封装成 MCP 工具供大模型自由调用。

## 约束与前置条件

- 应用仅在本机运行，但在用户配置后可以访问外部 API；
- 高德和和风天气账户、应用、Key 以及可用配额尚未创建；
- `deepseek-v4-flash` 是已确认的项目模型 ID，但真实鉴权、可用性、响应能力和限额尚未验证；
- 外部数据覆盖范围、字段、时效和服务条款必须在对应接入任务中以控制台和官方合约为准；
- 未取得真实数据前，测试替身只能证明本地行为，不能证明第三方服务可用。

## 产品风险

- 外部数据可能缺失、过期、相互冲突或不能覆盖全部费用；
- POI 不代表实时营业、价格或库存，用户可能误把基础地点信息当作交易信息；
- 未来日期的天气和交通具有天然不确定性；
- 大模型可能产生格式错误、无来源结论或不满足约束的计划；
- “已知费用合计”可能被误解为完整预算，需要在 UI 中持续显示未知项；
- 局部重规划如果影响分析不准确，可能破坏已确认的跨日安排。

这些风险通过数据来源记录、显式费用状态、代码校验、影响范围计算、人机确认和失败降级共同控制。
