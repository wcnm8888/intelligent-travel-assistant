# F-018 推荐优先、路线锚点闭环与方案有效对比

## 状态

`DONE / IMPLEMENTED / PASS / OFFLINE`

## 用户测试问题

- 单纯请求自然景点推荐时，顾问连续重复索取尚未决定的旅行偏好。
- 点击区域景区后显示类似加载的状态，但实际需要用户再次搜索并选择入口，缺少明确下一步和恢复出口。
- 多个方案展示相同总交通时间，名称却暗示明显优劣，且卡片没有呈现每日安排差异。
- 顾问面板的建议出现在长对话和输入区之后，用户难以完成确认动作。

## 设计原则

1. 探索意图先满足，规划约束逐步披露；“其他都灵活”是合法完整输入。
2. Agent 建议和 Provider 候选均不自动写入选择，用户确认仍是唯一写入口。
3. 区域语义地点与路线锚点分开保留，但界面必须把第二步呈现为选择任务，而不是计算状态。
4. “最多三个方案”不是必须三个；只有真实不同且能解释取舍的方案才展示。
5. 地点、路线、时间和可行性继续由确定性程序与 Provider 事实负责。

## Step

| Step | 目标 | 状态 |
| --- | --- | --- |
| Step 1 | 真实测试问题、基线和方案冻结 | DONE |
| Step 2 | 顾问发现、锚点闭环、方案比较和相邻测试 | DONE |
| Step 3 | Development、synthetic 浏览器与离线收口 | DONE |

## 实施结果

- 明确推荐意图会先执行一次 session 预算内的只读 POI 发现，模型收到 `recommendation_requested` 后必须先返回候选，未提供的偏好按灵活处理。
- 前端同步复用该搜索缓存，把建议地点显示在列表和地图中；接受前不进入选择，确认后才增加 revision。
- 区域景点自动搜索入口并只显示 point/verified 候选；支持取消、空结果恢复，完成后显示“路线入口已确认”。
- V6 每个优化目标只保留一个真实命中的不同日程，不用任意排列补满三项；卡片展示每日地点、日交通和最忙一天。
- 顾问建议前置，最近四条对话直接展示，较早消息默认折叠。

## 验证结论

- 后端两轮定向均为 9 项通过；前端两轮分别为 9、10 项通过，锚点最终回归 1 项通过。
- 首个 desktop synthetic 产品旅程完成后因脚本检查时点失败，证据保留且 mobile 未启动；只修复该时点后，desktop 与 390px 新批次均通过。
- 第一次 Development 仅文档状态投影失败；一次只读诊断与最小投影修复后，新 Development 完整通过所有后端/前端测试、构建和文档合同。
- 真实地图、高德、DeepSeek、和风调用均为 0；真实 UAT 为 `NOT_EXECUTED / NOT_AUTHORIZED`。

## 验收场景

- 用户发送“帮我推荐一些自然景点，其他都灵活”，系统最多执行一次受控只读 POI 搜索并返回最多三个待确认地点；不要求先填写完整偏好。
- 用户点击区域景区后自动获得具体入口候选；只允许 point/verified 候选作为 route anchor，可取消且无结果时有清晰提示。
- 相同总交通但每日负担不同的方案显示每日地点和分钟；同一优化目标命中同一日程时不复制卡片。
- 所有建议在接受前不进入 selection、solver、Prompt 允许集合或结果。
- desktop 与 390px、地图失败降级、键盘操作和 loopback 网络门禁通过。

## 边界

不新增 Provider、Agent 框架、依赖、数据库、持久化或多城市能力；不执行真实地图、高德、DeepSeek、和风调用；不执行 Git 交付。
