视觉方向采用“城市旅笺 / field journal”：米纸色背景和墨蓝信息骨架承载计划，朱红提示硬冲突，青绿色表示可信来源。来源、时效、费用可信状态和 unknown 与行程同级展示，不下沉为页脚免责声明。

参考稿可切换 `initial`、`processing`、`ready`、`partial`、`conflict`、`needs_input`、`failed`：

- 输入区明确目的地、日期、人数、总预算、偏好、节奏、交通、住宿、用户住宿费用与餐饮预算；餐饮默认 `100 元/人/天` 且可修改；
- 处理中显示规范化、数据收集、结构化规划和确定性校验阶段，不使用无说明的无限转圈；
- `partial` 对未完成路线、天气和金额逐项标为未验证/未获取/未知，unknown 不显示为 `¥0`；
- `conflict` 保留代码裁决和已知费用构成，不自动放宽预算，并只展示与该裁决一致的三类来源；
- `needs_input` 要求用户补充明确住宿区域或 POI，不猜测位置或暗示酒店库存；
- `failed` 仅显示安全错误类别、影响与恢复动作，不显示原始响应、凭证或内部异常；
- 桌面采用左侧输入、右侧结果；窄屏优先显示结果并折叠输入，初始态则自动展开输入；所有状态都有文字含义和可见键盘焦点，不只依赖颜色。

Step 21 本地设计 QA 已确认：两种目标视口可读，`390px` 文档宽度等于视口宽度、无水平溢出；七种视图可切换；终态关键文案、unknown、来源数量和恢复动作可观察；控制台无错误或警告；浏览器只读取本地静态资产。Step 22 用户批准同时确认了视觉方向、信息顺序、文案和桌面/窄屏布局。

### 冻结范围与允许偏差

Step 23–27 必须保持以下产品语义：信息层级、桌面双栏、窄屏结果优先/输入折叠、七种视图、可信状态标签、unknown 规则、来源与时效可见性、安全错误和恢复动作。未经新的产品批准，不得删除状态、隐藏 unknown、弱化来源、把 partial 表述为完整成功，或加入地图、图片、预订、支付、登录和外部前端调用。

生产 React 实现允许在不改变上述语义的前提下进行组件拆分、使用语义化 HTML、调整实现细节、补充自动化测试、改进键盘/读屏体验，并为 `720px` 以下连续宽度做必要的间距和换行适配。若 API 实际字段要求改变信息层级、关键文案、状态含义或用户动作，必须停止并重新取得设计批准。

## 设计目标

- 让用户在一个清晰流程中输入需求、查看计划、理解冲突并发起局部修改；
- 让数据来源、更新时间、费用可信状态和未知项与行程内容同等可见；
- 在外部服务失败时保留可用结果，明确说明影响和恢复动作；
- 在跨日、跨城或住宿变更前展示影响范围并取得确认；
- 桌面优先，同时保证窄屏下可读和可操作；
- 不依赖复杂地图、图片或装饰性动画完成核心任务。

## 核心用户故事

```text
作为自由行用户，
我希望输入旅行约束并得到可校验的逐日计划，
以便在自行预订前做出有依据的选择。
```

```text
作为预算敏感的用户，
我希望看到费用来源、可信状态和未知项，
以便不把不完整合计误认为真实总价。
```

```text
作为需要调整计划的用户，
我希望只修改某一天或某个景点，
以便保留其他已经确认的安排。
```

## MVP 信息架构

第一版使用单一旅行规划工作台，不建立复杂多页面导航：

```text
顶部：项目状态 / 当前计划版本 / 数据更新时间
├─ 需求输入区
├─ 处理进度与失败提示
├─ 计划摘要
│  ├─ 日期与城市
│  ├─ 已知预算 / 未知项
│  └─ 关键天气与冲突
├─ 逐日行程
│  ├─ 活动与 POI
│  ├─ 交通段与预计耗时
│  ├─ 费用项
│  └─ 当日来源与警告
├─ 来源与不确定性
├─ 冲突与待确认事项
└─ 局部重规划操作
```

复杂地图、相册、PDF 预览、预订入口和账户设置不出现。

## 主流程

### 创建计划

1. 用户填写目的地、日期、人数和总预算；
2. 用户补充兴趣、节奏、交通和住宿要求；
3. 前端执行格式校验，提交到后端；
4. 系统分阶段展示“规范化需求、获取数据、生成计划、代码校验”；
5. 缺少必要硬约束时，界面回到对应字段并说明原因；
6. 成功时展示计划；部分数据缺失时展示 `partial` 结果和恢复动作；
7. 用户检查预算、来源、警告和冲突，再决定是否调整。

### 局部重规划

1. 用户在某一天或某个活动上选择替换、删除、调整时间或补充要求；
2. 系统显示预计影响范围；
3. 只影响当天内部时，可直接执行并显示变更摘要；
4. 影响住宿城市、跨城交通或相邻日期时，显示受影响日期和原因；
5. 用户确认后才生成新计划版本；取消则保留原版本；
6. 新旧版本显示变化项，不把未受影响日期伪装为重新验证。

### 外部服务失败

1. 保留已经成功获取和验证的数据；
2. 在对应模块显示 provider、错误类别和影响，而不是全页空白；
3. 可重试错误提供明确的重试操作；
4. 配置缺失或鉴权失败指向本地配置说明，不反复自动请求；

### Provider 归因与生成内容披露

1. 展示和风天气数据的页面必须清晰显示“天气服务由和风天气驱动”及 `https://www.qweather.com` 链接；
2. 和风响应要求随数据展示的 attribution 必须与对应天气或预警共同、原样显示，不得被摘要、翻译或丢弃；
3. 使用高德真实 POI 或路线前必须完成具体使用场景的许可核对，并按许可显示“高德地图”来源；未经澄清不保存真实数据截图或持久缓存；
4. DeepSeek 生成的候选计划和解释必须明确标注为 AI 生成，并继续提示其已由确定性规则校验但仍可能不准确；
5. 不能安全生成计划时停止并说明还需要什么。

## 输入契约方向

| 输入 | 控件方向 | 必要性 | 主要校验 |
| --- | --- | --- | --- |
| 目的地 | 城市/地点输入与候选确认 | 必填 | 不能只保留歧义文本，需确认规范地点 |
| 开始与结束日期 | 日期范围 | 必填 | 开始不晚于结束，跨度在产品允许范围内 |
| 同行人数 | 正整数输入 | 必填 | 大于 0，面向小型同行群体 |
| 总预算 | 金额与币种 | 必填 | 金额大于 0，MVP 默认 CNY |
| 兴趣偏好 | 多选和补充文本 | 选填 | 区分偏好与必须条件 |
| 行程节奏 | 单选 | 选填 | 舒缓、均衡、紧凑等受控值 |
| 城际/市内交通要求 | 受控选项和补充文本 | 选填 | 保留禁用方式和硬约束 |
| 住宿要求 | 区域、设施、预算或用户价格 | 选填 | 不暗示实时库存或可订 |
| 其他限制 | 文本或结构化选项 | 选填 | 长度限制，不作为系统指令执行 |

真实 API 和领域 Schema 在对应实现任务中确定。前端类型不能代替服务端和领域校验。

## 输出与组件契约方向

### 计划摘要

必须展示：

- 目的地、日期范围、人数和计划版本；
- 当前状态：`ready`、`partial` 或 `conflict`；
- 已知费用合计、预算、未知费用项数量；
- 关键天气风险、主要冲突和待确认事项；
- 最近数据更新时间。

存在未知费用时，不显示“预算充足”这种完整结论，只显示已知部分与预算的关系。

### 逐日计划

每天展示：

- 当地日期、城市和住宿区域/地点；
- 按时间排序的活动、POI、预计停留和费用；
- 活动之间的交通方式、预计距离和时间；
- 天气提示、警告、冲突和未验证项；
- 当天可执行的局部修改入口。

POI 卡片不得显示“可订”“最低价”或“营业中”，除非未来接入能证明这些字段的权威数据源。

### 来源与不确定性

来源可以按字段或记录关联，界面至少可查看：

- provider 名称；
- 获取时间；
- 有效期或“有效期未知”；
- 费用可信状态；
- 数据缺失、过期、估算假设或冲突警告。

不得只在页脚放一个笼统“数据来自第三方”的说明。

### 影响确认对话框

必须包含：

- 用户请求的修改；
- 受影响日期、城市、住宿和跨城交通；
- 将保留与将重新计算的范围；
- 可见的确认和取消操作；
- 取消后原计划不变的说明。

默认焦点和按钮文案不能诱导用户无条件确认。

## 页面状态

| 状态 | 用户看到 | 可用操作 |
| --- | --- | --- |
| `initial` | 空白需求表单和必要说明 | 填写 |
| `editing` | 已输入内容和字段校验 | 修改、提交 |
| `submitting` | 请求正在提交 | 取消重复提交 |
| `normalizing` | 正在检查和规范需求 | 等待 |
| `needs_input` | 缺失字段和原因 | 补充后继续 |
| `collecting` | 正在获取地点、路线和天气，显示分项进度 | 可取消当前流程 |
| `planning` | 正在生成结构化计划 | 等待 |
| `validating` | 正在执行代码校验 | 等待 |
| `ready` | 完整计划和校验摘要 | 查看、局部修改 |
| `partial` | 可用计划、缺失数据和影响 | 查看、补充、重试 |
| `conflict` | 不能自动解决的冲突 | 调整约束或确认影响 |
| `awaiting_confirmation` | 影响范围与确认内容 | 确认或取消 |
| `replanning` | 正在生成新版本 | 等待，保留旧版本 |
| `error` | 错误类别、影响和恢复动作 | 重试、返回编辑或查看部分结果 |

加载状态不能只显示无限转圈；应说明当前阶段。可重试与不可重试错误必须有不同动作。

## F-003 局部重规划交互（已实现并交付）

F-003 延续现有结果优先页面，不新增历史计划页、版本页或独立路由。桌面端在计划结果区域内打开右侧局部调整面板；`390×844` 下该面板按文档流堆叠为全宽区域，不使用超出视口的固定宽抽屉。原计划在整个分析、确认和执行期间保持可见，只有 completed 后替换为新当前计划。

### 入口与命令编辑

- 每个活动提供“替换活动”“删除活动”“调整时间”；每日标题提供“调整当天顺序”；
- 替换只选择 1–3 个结构化类别，不提供任意 Prompt 或 provider 地点 ID 输入；
- 删除先显示目标活动和保持原计划的取消动作；
- 时间编辑使用当地时间并就地提示起止错误，不允许改变日期；
- 重排必须包含当天全部活动，键盘用户可用明确的上移/下移操作，不能只依赖拖拽；
- 提交后立即禁用同一 command 重复提交，但取消和查看原计划仍可用。

### 面板状态

| UI phase | 展示与行为 |
| --- | --- |
| `editing_command` | 结构化字段、目标活动/日期、取消和“分析影响” |
| `analyzing` | 阶段文案；原计划不变；不宣称正在调用 Provider |
| `auto_replanning` | 明示“低影响修改正在重新校验”；保留 baseline |
| `awaiting_confirmation` | 影响分类、日期/活动、路线、预算、来源 reuse/refresh/drop、将保留内容、15 分钟到期时间 |
| `deciding` | 禁用重复确认/取消；仍显示原计划 |
| `expired` | 明示确认已失效，只能重新分析或关闭；不得继续执行旧决定 |
| `needs_input` | 显示安全缺失项并保留原计划；不自动扩大请求 |
| `conflict` | 显示硬冲突和受影响 refs；原计划继续可用 |
| `failed` | 显示安全错误和可恢复动作；不显示 provider body |
| `completed` | 切换当前计划，展示本次 baseline→result change set 和 ready/partial 状态 |
| `version_conflict` | 明示计划已变化，要求基于当前计划重新发起；不自动 rebase |
| `cancelled` / `rejected` | 说明未改变计划并恢复触发入口焦点 |

### 确认与差异

- 确认标题必须表达“将影响哪些内容”，不能使用默认诱导式“继续即可”；
- approve 与 cancel 都是清晰文本按钮，默认焦点落在面板标题或影响摘要，不自动落在 approve；
- unknown 费用显示“金额未知”，不得显示 `¥0`；预算风险同时显示已知合计、未知项数和是否可判定；
- 来源动作逐类展示 reuse/refresh/drop 及 freshness，不把 unknown validity 变成 fresh；
- completed 只展示此次新增、删除、变更活动及路线/时间/费用/来源变化，不提供任意历史版本比较；
- partial 必须持续显示 warning/uncertainty，不得使用 ready 的完成文案或样式。

### 可访问性与视觉门禁

- 状态、风险和来源动作均以文字/图标组合表达，颜色不是唯一信号；
- 面板使用可读标题和 live region 宣告 analyzing、awaiting confirmation、completed 和失败变化；
- 打开面板后焦点移到标题，关闭/取消/完成后恢复到发起活动或日期入口；
- 确认过期倒计时不是唯一提示，服务端时间为事实来源；
- 桌面和 `390×844` 必须验证无水平溢出、全部主操作可键盘到达、重复提交被阻止、原计划在 pending/failed/cancelled 可继续阅读；
- Step 6 实现前必须由用户审查本冻结设计；实现后的浏览器视觉验收不能由组件测试替代。

## F-004A 单城市 2–7 日交互（Step 1 冻结，Step 5 已实现）

F-004A 继续使用当前单页、结果优先布局，不新增历史页、版本页、地图页或多城市路线编辑器。legacy 双日请求仍显示原交互和原请求形状；用户显式使用结束日期后，前端提交 version 2 请求。

### 日期与逐日窗口

- 表单新增有标签的结束日期控件；默认开始日期沿用现有规则，未被用户编辑的结束日期跟随为开始日 +1；用户一旦编辑结束日期，后续开始日期变化不静默覆盖，只显示可定位错误；
- 有效范围为含首尾 2–7 日；结束日早于/等于开始日、超过 7 日、开始日不在既有 D+1 至 D+5 或日期无法解析时禁止提交并聚焦首个错误；
- 每个日期显示一组本地开始/结束时间，标题同时显示“第 N 天”和完整日期；offset 不直接展示给用户；
- 初始窗口沿用现有体验：第一天 `09:00–20:00`，其余天 `09:00–18:00`；用户编辑值在日期仍存在时保留，缩短行程只移除尾部窗口；
- 跨夜、零时长和反向窗口在字段附近提示；前端提示不替代服务端 2–7 日和窗口全集校验。

### 结果信息架构

- 摘要显示城市、开始/结束日期、总天数、人数、预算判定、unknown 数和来源状态，不再使用固定“双日旅笺”文案；
- 日期导航采用可换行的按钮/链接列表或原生选择控件，不能依赖横向拖动；每项有完整可访问名称，当前日同时用文本和 `aria-current` 表达；

## F-005 同 shape 失败与恢复交互（Step 1 冻结）

F-005 不新增页面、公开 response 键或前端自定义终态。现有 legacy/V2/V3 strict parser 继续拒绝额外/缺失键；前端只使用服务端给出的 `status`、`retryable`、`errors`、`uncertainties`、`sources` 和 `attempt`，不自行计算 freshness、Provider 关键性、fallback 或终态。

### 信息顺序与动作

| 服务端结果 | 首要标题 | 必须显示 | 主恢复动作 |
| --- | --- | --- | --- |
| `needs_input` | 需要补充信息 | 安全字段问题和已保留输入 | 返回修改并聚焦首个可修正字段 |
| `conflict` | 约束无法同时满足 | 确定性冲突摘要，不混入 Provider 猜测 | 返回修改约束 |
| `failed` + 鉴权 | 本机服务配置需要检查 | Provider 名称、固定安全说明；不显示秘密状态值 | 返回修改/检查本机配置，无 retry |
| `failed` + timeout/rate/unavailable | 暂时无法完成计划 | 已验证到的来源、失败影响和 attempt | `retryable=true && attempt<3` 时显示既有重试 |
| `partial` | 计划可用，但信息不完整 | 可执行计划、具体缺口、来源 freshness、unknown 费用 | 查看计划；允许时提供次要重试 |
| `data_stale` | 数据可能已经变化 | 来源、获取时间、stale 标签及被剔除/受影响能力 | 允许时重新获取；路线 stale 无计划时按 failed 展示 |
| `unknown_validity` | 有效期未知 | 来源获取时间和“不代表 fresh”文案 | 不因该标签单独提供 retry |

错误信息排序固定为：用户可修正输入 → 确定性冲突 → 配置问题 → 可重试暂时失败 → stale → 不可重试数据/模型错误。状态优先级仍为 `needs_input/conflict/failed/partial/ready`，不能因 error 数量或颜色改变服务端终态。

- `retryable` 表示原因可重跑；按钮还必须满足 `attempt < 3` 且当前没有请求。点击沿用既有 retry URI、loading/live-region、禁用和焦点恢复，不在浏览器执行 HTTP attempt retry。
- `provider_unauthorized` 的文案只说“检查本机该服务配置”，不展示环境变量值、Key 是否部分匹配或原始错误。Schema/model invalid 不展示原始响应，并且不提供盲目自动重试。
- stale/unknown 不能只用颜色；source card 同时显示中文状态和 `fetched_at`。optional stale 已从计划剔除时仍在缺口摘要说明影响，不用空卡伪装正常内容。
- unknown 金额始终显示“未知”，amount 为空；不显示 `¥0`，不把已知合计描述为完整总价。
- F-003 replan 和 V3 scope 文案不变；V3 用户城际来源继续显示“用户提供，未核验”，不能误写成 stale Provider。

Step 6 组件门禁覆盖全部恢复组合、错误排序、attempt 3、parser exact keys、legacy/V2/V3 和 390px。Step 7 loopback synthetic 浏览器再验证 desktop/390px、键盘/焦点、live region、无水平溢出、console 0 error/warning 和所有网络仅 loopback；这些仍不是视觉改版或真实 Provider UAT。

Step 6 已完成：前端仍只消费既有字段，鉴权失败显示本机配置问题且无 retry；暂时失败继续受 `retryable && attempt<3` 控制；stale 显示获取时间、过期标签和“重新获取数据”；unknown-validity 明示“不代表当前有效”且不凭空产生 retry。错误按冻结优先级显示，但不改变服务端终态或 freshness。定向 30 项、前端全量 99 项和全部静态/build 门禁通过；desktop/390px 真浏览器与独立审查仍属于 Step 7。
